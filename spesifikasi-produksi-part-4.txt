Pendekatan Materi: Memadukan Analogi Kasir Cepat Saji yang Ikut Memasak di Meja Depan vs Dapur Belakang Berbasis Nomor Antrean dengan bedah pola Producer-Consumer BullMQ, kode respons HTTP 202 Accepted, pembatasan konkurensi Worker, serta mekanisme Exponential Backoff.

Tujuan Komunikasi: Mengungkap strategi pemulihan otomatis (Self-Healing) menggunakan Exponential Backoff di BullMQ ketika panggilan API model AI mengalami gangguan jaringan atau Rate Limit (HTTP 429) di tengah pemrosesan dokumen panjang.

Spesifikasi Visual: Linimasa pemrosesan 300 potongan teks dari sebuah PDF. Saat tiba di potongan ke-150, API Gateway AI mengembalikan error merah `429 Too Many Requests`. Alih-alih menggugurkan seluruh dokumen, konfigurasi BullMQ `attempts: 3, backoff: { type: 'exponential', delay: 5000 }` menahan Worker untuk beristirahat selama 5 detik (percobaan 1), 10 detik (percobaan 2), hingga 20 detik (percobaan 3), lalu melanjutkan proses dari potongan yang belum tersimpan di PostgreSQL.

Teks Layar: "API AI Kena Rate Limit di Halaman 75? Pulihkan Otomatis dengan Exponential Backoff (5s -> 10s -> 20s)!"

Spesifikasi Visual: Layar atas menampilkan memori Redis DB 0 yang perlahan penuh oleh ribuan bangkai data JSON dari Job yang sudah berstatus selesai berminggu-minggu lalu karena data BullMQ tidak memiliki TTL. Layar bawah menampilkan potongan konfigurasi `defaultJobOptions` pada BullMQ: `removeOnComplete: { count: 100 }` (hanya simpan 100 riwayat sukses terakhir di Redis) dan `removeOnFail: { age: 86400 }` (hapus log gagal setelah 24 jam), karena rekam jejak permanennya sudah tercatat aman di tabel `documents` PostgreSQL.

Teks Layar: "Awas Bangkai Job BullMQ Bikin Redis Penuh! Wajib Pasang `removeOnComplete` & `removeOnFail`"
